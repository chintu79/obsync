## Server behavior

- `obsync-httpd` serves the dashboard (port 42021, embedded `webui.html`) and the P2P sync TCP server (port 42042). It keeps the selected vault and approved devices **in memory** — restarting the daemon loses the vault selection (re-select via `POST /api/select-vault`) but approvals persist in `~/.obsync-approved.json`.
- The sync server calls `engine.refresh_index(true)` before every session so files created/edited directly on the laptop disk reach the phone. Do NOT revert to a DB-only manifest.
- `refresh_index(detect_deletions)` gates auto-tombstoning: the laptop server is authoritative and passes `true`; the phone client passes `false` (additive-only) because its disk may be an incomplete replica — a phantom tombstone from the phone can delete files on the authoritative vault (see `core/src/android.rs` `syncOnce`).
- Conflict model: revisions are per-engine local counters, so "revision > 0 on both sides" must NEVER be treated as "both changed since last sync" (any hash difference would be a permanent false conflict). The correct signal is `file_states.synced_hash` (the content hash the last sync agreed on, v2 schema column): conflict only when BOTH sides changed since their agreement (`core/src/conflict/detector.rs` `resolve_divergence`); rows with NULL `synced_hash` (pre-v2) fall back to newer-mtime-wins. `record_remote_file`, `mark_synced`, and `apply_update` set `synced_hash`; `refresh_index` preserves it across local edits. The client diff (`sync/peer.rs` step 3) is the single decision point — the server accepts pushes unless it has unsynced local edits.
- Selective sync ("sync scope", `core/src/sync/scope.rs`): a `Scope` is a list of `ScopeEntry { kind: File|Folder, path: "/"-separated rel }`; an EMPTY scope means whole vault (consumer reads `is_everything()`). No wire/protocol changes: the server builds a scoped manifest (`engine.build_manifest_scoped`) and the client passes `engine.local_scope()` (config key `local_scope`, JSON `Scope`). The absence-without-tombstone hazard (a filtered-out path looks "new" to the other side) is solved by BOTH sides filtering + hard server guards: `serve_file` aborts the session on out-of-scope requests; `handle_server_operation` skips rejected ops (0|1) and calls `drain_file_data` to keep TCP framing aligned; read-only devices reject pushes/deletes but still get served. Scopes live in `shared_scope` (vault-wide, every approved device), `device_scopes` (per fingerprint, on top of shared) and `device_flags.read_only`; effective = shared ∪ device, but if BOTH are empty the device sees the whole vault (backward compat — `Scope::merge` is a plain union, it must NEVER shortcut empty→everything). Persisted in the vault DB; approved map in httpd is keyed by fingerprint, matching scopes. Server callers pass `effective_scope(&fp)` + `device_read_only(&fp)`; the phone client (`android.rs` `syncOnce`) passes `Scope::everything()` (additive-only, no server role). Dashboard API: `GET /api/scopes`, `POST /api/scopes/shared` `{entries}`, `POST /api/devices/:fingerprint/scope` `{entries, read_only?}` (rejects unknown fingerprints), `/api/devices` enriched with per-device `scope` + `read_only`; `handle_devices` must clone the `approved` tokio MutexGuard before locking the engine Mutex (a std guard held across await breaks Send). `webui.html` renders a "Sync scope" card: one shared-selection editor + one editor per approved device (folders are derived client-side from `/api/files` prefix grouping; selecting a folder covers future files under it).
- `run-server.sh` builds + starts the server and opens the dashboard (release binary unless `--debug`).
- Dashboard (httpd) keeps an in-memory activity ring (`AppState.activity`, cap 100) + per-fingerprint `last_seen` heartbeat for online/offline. Activity events are recorded on: vault select, device connect/approve/reject, sync-session end (pushed/pulled/conflicts), conflict resolve, snapshot restore. Both are lost on daemon restart (like the vault selection); `/api/status` enriches with `conflicts`, `pending`, `devices.{total,online}`, `last_sync_at` (most recent `sync` activity) and `vault.path`. Live updates are pushed to the dashboard over SSE (`/api/events`, a tokio broadcast channel fed by `record_activity`); the UI uses `EventSource` and keeps slow polling (15s/30s) as a safety net — jsdom has no EventSource so verification exercises the polling path. Non-pairing endpoints: `/api/status`, `/api/select-vault`, `/api/sync-now` (authoritative `refresh_index(true)`), `/api/reveal-vault` (xdg-open), `/api/browse-vault` (native zenity folder picker via `spawn_blocking`; headless → `cancelled` and UI falls back to manual path entry), `/api/files`, `/api/devices`, `/api/activity`, `/api/events` (SSE), `/api/conflicts`, `/api/conflicts/resolve`, `/api/versions`, `/api/restore`, `/api/identity`, `/api/pairing-qr`, `/api/pending`, `/api/approve/:id`, `/api/reject/:id`.
- The dashboard is a single-file `httpd/src/webui.html` (no React/Tailwind/build step; inlined `qr-code-styling` in the first script block — keep it inline, no CDN, the hotspot has no internet). It shows a first-run "Connect your phone" wizard (QR + 3-step checklist) until the first device is approved (`/api/status` `devices.total == 0`), which collapses into an inline approve/reject prompt while `pending > 0`; `renderQr` is container-per-instance (stores the styler on `el._obsyncQr`) so the wizard and pair card each render their own QR. It is served via `include_str!` — editing the file requires rebuilding `obsync-httpd` and restarting (ritual: `pgrep -x obsync-httpd | xargs -r kill` to avoid the pkill self-match quirk). UI verifies against the live server with a jsdom harness (`/tmp/opencode/verify.js`): stub `fetch` in `beforeParse`, and `process.exit(0)` at the end or the `setInterval`s keep node alive; jsdom can't decode the QR logo data-URI so `qr logo image` legitimately reads FAIL there, and it can't compute `grid-template-columns` (breakpoint visuals need a real browser).
- CI: `.github/workflows/ci.yml` (push/PR checks), `.github/workflows/release.yml` (tag `v*` → APK + Linux/macOS/Windows server binaries + desktop app installers + GitHub Release).
- Dependencies: keep third-party crates minimal — a dependency must not exist for a single one-off use when std will do. `core` uses only tokio, serde/serde_json, blake3, rusqlite (bundled), x25519-dalek + aes-gcm (sync encryption), sha2/hex/bincode/rand, anyhow, tracing; `httpd` adds axum, tower-http, futures-core, qrcode. P2P sync is a hand-rolled protocol (`core/src/network/peer.rs`) — no QUIC/Noise/mDNS/notify. File changes are picked up by `refresh_index(true)` before each sync session, not by a filesystem watcher.
- KNOWN FLAKY (historical, module removed): `core/src/sync/transfer.rs` `test_send_receive_small_file` failed intermittently (~50%) at `--test-threads=32` with `dest.md` empty on disk; never reproduced after debug instrumentation was added then removed. The transfer module was deleted in the dependency audit, so this is moot unless a chunked-transfer path is ever reintroduced.
